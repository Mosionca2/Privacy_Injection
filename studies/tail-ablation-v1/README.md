# Neutral-tail follow-up, version 1

This separately frozen exploratory follow-up uses two existing fingerprinted local snapshots and fresh synthetic identifiers/entity names. The original study outcomes were already known when this extension was specified. Neither original scientific freeze is changed.

Three conditions use the same boundary policy and retrieved records: D1 is the original boundary prompt; D2 adds the existing reminder and repeats the question; N replaces that reminder sentence with a neutral description and repeats exactly the same question. All **960 N/D2 prompt pairs per model have identical encoded input lengths**; maximum input length is 365 tokens. The static neutral sentence was selected using tokenization before any new model outcomes. One neutral sentence does not represent all possible length controls. N-D1 combines added length with repeated questioning; D2-N compares sentence content while controlling those two features.

The new dataset contains 24 development and 96 test cases, with eight queries per case/condition and three conditions per model. Planned fresh generations are **1,152 development plus 4,608 follow-up test responses**, in twelve real GPU captures. These follow-up test responses are separate from the original 6,144 formal responses. Comparisons are paired, descriptive stratified bootstrap contrasts, without multiplicity-adjusted confirmatory claims.

The protocol, both prompt inventories, data, model identities, inference/scoring source and exact dependencies were frozen before any follow-up generation. The fixed batches reuse previously measured settings (64 for the local 8B snapshot and 16 for 1.7B). Development must complete without infrastructure errors, truncation or output-cap events before test execution. No prompt, condition or batch is selected from development leakage outcomes.

The real inference entry point is `python -m tail_ablation.run --model assets/model --study-model primary --defense N --split dev --batch-size 64` in an independent recording workspace. Materialize the pinned ReproLLM package and actual local weights first, generate the matching declaration through `tail_ablation.record.manifest`, create a fresh offline lock, commit inputs and run through ReproLLM. The per-condition captures retain actual declarations, snapshots, output hashes, run IDs, audit findings and selected exports. Model files, machine paths and private configuration are not distributed.

The prompt inventories save message text, rendered-text hashes, encoded-token hashes and lengths. The runner re-renders and re-encodes each actual padded batch and checks its unpadded token IDs before generation. ReproLLM's input-consumption field retains its own `unverified` contract; the scientific runner's checks provide additional, specifically scoped evidence.
